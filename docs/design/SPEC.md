# 포트폴리오 화면 명세

이 문서는 화면의 각 요소가 **왜 그 자리에 있는지** 기록한다. 고칠 때는 먼저 해당 항목의 "왜"를 읽는다. 이유가 여전히 맞으면 위치를 지키고, 이유가 바뀌었으면 이 문서를 먼저 고친 뒤 화면을 고친다.

- 기준일: 2026-10-29
- 대상 페이지: `/itIsMe/` 한 장 (보조 경로 `/work/`, `/about/`는 이 페이지의 앵커로 이동)
- 콘텐츠 정본: `src/data/portfolio.json`, `src/data/site.json`
- 코드 지도: [docs/architecture/04-code.md](../architecture/04-code.md)

---

## 1. 이 페이지가 답해야 하는 것

채용하는 사람은 포트폴리오로 "이 사람에게 일을 맡기면 어떻게 될까"를 추정한다. 그 질문은 세 가지로 압축된다.

| 질문 | 찾는 증거 | 이 페이지에서 답하는 곳 |
|---|---|---|
| 끝까지 만들 수 있는가 | 배포, 동작하는 화면, 맡은 범위 | Case 01 음식 사진 분석 서비스 |
| 스스로 판단하는가 | 문제 정의, 대안 비교, 근거 있는 선택 | Case 02 농산물 가격 예측 |
| 함께 일할 수 있는가 | 공유, 문서화, 역할 분담 | Case 03 항공기 엔진 수명 예측 (+ Case 01 협업 방식) |

읽는 사람마다 머무는 곳이 다르다. 배치는 이 차이를 전제로 한다.

| 읽는 사람 | 먼저 보는 것 | 배치 원칙 |
|---|---|---|
| 채용 담당자 (30초) | 누구인가, 무슨 일을 하는가, 대표 작업 | 첫 화면과 질문 목록만 읽어도 판단이 끝나야 한다 |
| 개발 팀장 (3분) | 문제의 난이도, 본인 기여, 판단 이유 | 사례마다 같은 위치에 문제→판단→실행→검증→남은 과제 |
| 동료 개발자 | 구조, 협업 흔적 | 사례의 "내가 맡은 일 / 팀이 함께한 일", 저장소 구성 |
| 기술 면접관 | 실제로 이해했는가, 한계를 아는가 | 펼쳐 보는 근거, "남은 과제", 원본 쪽 번호 |

**배치 규칙:** 위로 갈수록 판단에 필요한 최소 정보, 아래로 갈수록 검증에 필요한 상세 정보. 상세는 숨기지 않고 접어 둔다.

## 2. 이전 작업에서 계승한 원칙

이전 결과물 두 가지(원본 PDF 22쪽, 직전 웹 포트폴리오)에서 잘 작동한 부분을 형태가 아니라 **원리**로 추출했다. 형태는 바뀌어도 원리는 지킨다.

### 2.1 시선은 자기소개를 향한다 — 원본 PDF p.2

- **관찰:** 사진 속 인물은 화면 오른쪽을 바라보고, 그 방향에 "저는 책임감과 꾸준함을 기반으로…"가 놓여 있다.
- **원리:** 사람은 얼굴이 바라보는 방향을 따라 시선을 옮긴다(시선 단서). 얼굴이 글을 보면 독자도 글로 간다. 얼굴이 바깥을 보면 독자의 시선도 페이지 밖으로 샌다.
- **적용:** 첫 화면에서 사진은 **왼쪽**, 자기소개는 **오른쪽**. 머리글의 작은 얼굴도 이름의 왼쪽에 두어 이름을 바라보게 한다. 모바일에서도 사진을 이름 왼쪽에 두어 같은 방향을 유지한다.
- **사진은 컬러 그대로:** 페이지 전체가 종이·먹·신호색 하나로 절제돼 있어, 자연색은 사진 하나뿐이다. 얼굴은 가장 먼저 시선을 끄는 대상이므로 첫 응시가 얼굴에 오고, 시선 방향을 따라 글로 넘어간다. 흑백으로 바꾸면 편집적이지만 사람이 멀어진다.
- **사진은 따라 내려오지 않는다:** 스크롤할 때 사진이 화면에 붙어 따라오면, 읽는 내용은 움직이는데 얼굴만 멈춰 있어 어지럽다(2026-10-29 피드백으로 제거). 화면에 고정되는 것은 머리글 하나뿐이다.
- **금지:** 사진을 좌우 반전하거나 글의 오른쪽에 두지 않는다. 사진을 바꾸면 인물이 보는 방향을 먼저 확인하고, 반대 방향이면 배치를 거울처럼 바꾼다.

### 2.2 주장 → 동기 → 증거의 순서 — 원본 PDF p.2

- **관찰:** 작은 도입문("흥미를 느끼는") → 굵은 주장("책임감과 꾸준함…") → 왼쪽 세로선이 있는 동기("AI에 매료되었습니다") → 상자 안의 증거(E2E, 11개월, 11개 프로젝트).
- **원리:** 사람 목소리로 시작해 숫자로 끝나야 믿을 수 있는 자기소개가 된다. 숫자만 있으면 이력서이고, 말만 있으면 다짐이다.
- **적용:** 첫 화면 오른쪽 열이 같은 순서다. 문장은 본인 원문을 그대로 쓴다(`about.lead`, `about.thesis`, `about.motivation`). 편집자가 지어낸 성격 묘사는 넣지 않는다.

### 2.3 근거 링크는 늘 같은 자리에 — 원본 PDF 모든 프로젝트 쪽

- **관찰:** 모든 프로젝트 쪽의 오른쪽 위에 "[발표자료 링크]"가 있다.
- **원리:** 확인 수단의 위치가 일정하면 찾는 비용이 0이 된다. 주장 바로 옆에 있으면 "확인해 볼 수 있다"는 신호 자체가 신뢰를 만든다.
- **적용:** 사례 머리 줄 오른쪽 끝에 "발표자료 ↗". 펼친 근거 안에도 한 번 더 둔다(긴 근거를 다 읽은 뒤의 자리).

### 2.4 시간에는 목소리와 종류가 있다 — 원본 PDF p.3

- **관찰:** 연표를 2025년과 2026년으로 나누고 각각 "쉬지 않고 달려왔습니다", "현재도 꾸준히 노력하고 있습니다"를 붙였다. 자격증은 색으로, 프로젝트는 "팀/개인"으로 구분했다. 2026년은 다른 색이다.
- **원리:** 연표는 날짜 목록이 아니라 속도와 지속성의 증거다. 해마다 한 줄의 목소리가 붙으면 숫자가 이야기가 된다. 종류를 구분하면 "공부만 했나, 만들었나"를 한눈에 본다.
- **적용:** 연도별 머리(`timelineYears`) + 항목 종류(`course` 교육 / `project` 작업 / `cert` 자격). 현재 연도는 강조색.

### 2.5 마지막은 인사로 닫는다 — 원본 PDF p.22

- **관찰:** "감사합니다 🙂"와 연락처만 있는 어두운 쪽.
- **원리:** 끝인사는 사람을 남긴다. 연락처는 행동을 남긴다. 둘이 같은 화면에 있어야 한다.
- **적용:** 어두운 연락처 장의 제목은 "읽어 주셔서 감사합니다." 바로 아래가 이메일. 이모지는 쓰지 않는다(글꼴·인쇄에 따라 모양이 달라짐).

### 2.6 미리보기는 정해진 자리에서 바뀐다 — 직전 웹

- **관찰:** 대표 프로젝트에 마우스를 올리면 오른쪽의 **고정된 이미지 영역**만 바뀌었다. "본문·링크 위에 떠다니는 이미지를 두지 않는다"는 결정이 기록돼 있다.
- **원리:** 커서를 따라다니는 이미지는 옆 줄의 글을 가리고, 손이 떨리면 화면이 떨린다. 자리가 고정되면 레이아웃이 예측 가능하다.
- **적용:** 질문 목록 오른쪽에 고정 미리보기 칸. 행에 마우스를 올리거나 키보드로 이동하면 그 칸만 바뀐다. 다른 작업 목록은 미리보기 없이 행마다 작은 썸네일을 항상 보여 준다(터치에서도 같은 정보).

### 2.7 같은 정보는 같은 자리에 — 직전 웹

- **관찰:** 사례마다 "내 역할 → 핵심 작업 → 팀 결과"를 같은 위치에 뒀다.
- **원리:** 두 번째 사례부터는 읽지 않고 훑는다. 위치가 같아야 비교가 된다.
- **적용:** 세 사례 모두 같은 골격(머리 → 메타 → 요약·결과 → 시각화 → 다섯 단계 → 역할 구분 → 근거). 사례에 따라 바뀌는 것은 시각화 하나뿐이다.

### 2.8 결론을 먼저, 그림은 그다음 — 직전 웹 모바일

- **관찰:** 모바일에서 요약을 도식보다 먼저 뒀다.
- **원리:** 무엇을 증명하는 그림인지 알아야 그림을 읽는다.
- **적용:** 모든 화면 크기에서 요약·결과 → 시각화 순서. DOM 순서와 화면 순서가 같아 화면 읽기 프로그램도 같은 순서로 읽는다.

### 2.9 결과에는 주체와 조건이 붙는다 — 직전 웹

- **관찰:** 결과를 `outcomeLabel`(팀 평가·팀 실험·구현 결과) / `outcome` / `outcomeNote`(해석 조건)로 나눴다. 0.98과 0.81을 직접 비교하지 않았다.
- **원리:** 팀의 숫자를 개인 성과처럼 보이게 하면 면접에서 무너진다. 조건을 먼저 밝히면 오히려 판단력의 증거가 된다.
- **적용:** 결과 칸은 주체(팀 평가·팀 실험·구현 결과) → 결과 → 조건 한 줄. 조건은 긍정문으로 쓴다(3.5).

### 2.10 길 찾기는 읽는 동안 보인다 — 직전 웹

- **관찰:** 넓은 화면에서 목차가 항상 보였고, 현재 장이 표시됐다.
- **원리:** 긴 한 장짜리 페이지에서 "지금 어디인가"를 잃으면 이탈한다.
- **적용:** 1100px 이상에서는 머리글이 스크롤해도 숨지 않는다. 좁은 화면에서만 아래로 스크롤할 때 숨기고 위로 올리면 다시 보인다(세로 공간이 귀하므로).

### 2.11 모든 그림은 주장 하나에 답한다 — 2026-10-29 피드백

- **관찰:** 근거 갤러리와 대표 이미지가 "그래서 이 사진이 뭔데?"로 읽혔다. 그림과 주장이 서로 다른 곳에 있었고, 그림 안에서 어디를 봐야 하는지 알려 주지 않았다.
- **원리:** 지친 사람은 그림을 해석하지 않는다. 주장 문장을 먼저 읽고, 그림에서 표시된 곳만 확인한다. 그림 하나가 주장 하나를 증명할 때 인지 부담이 가장 낮다.
- **적용:** 사례마다 "증거 01–05"(대표 사례는 5개, 나머지는 4개). 각 줄은 왼쪽에 주장(한 문장)과 왜 중요한지(한 줄), 오른쪽에 그림. 그림에는 번호 붙은 사각형 표시가 있고, 그림 아래에 같은 번호로 "여기서 볼 것"을 적는다. 표시는 그림당 최대 3개.
- **금지:** 설명 없는 이미지 나열(갤러리). 그림을 추가하려면 먼저 그 그림이 증명하는 주장을 쓴다. 주장이 없으면 그림도 넣지 않는다.

### 2.12 계승하지 않은 것

| 이전 요소 | 버린 이유 |
|---|---|
| 프로젝트별 기여도 점(●●●○) | 자기 평가 점수는 근거가 아니다. 대신 "내가 맡은 일" 목록 |
| 사진 확대 대화상자 | 사진이 첫 화면에서 충분히 크다. 같은 사진을 두 번 여는 동작은 정보가 없다 |
| 스크롤에 고정되어 단계가 바뀌는 시각화 | 스크롤 속도가 내용을 결정한다. 직접 누르는 전환(분할 데모, 슬라이더)으로 바꿨다 |
| 커서를 따라다니는 이미지(직전 재설계) | 2.6 위반 |
| 스크롤을 따라오는 사진, 따라오는 미리보기 칸 | 읽는 흐름과 다른 속도로 움직여 어지럽다 |
| 설명 없는 근거 이미지 갤러리 | 2.11 위반 |

## 3. 전역 규칙

### 3.1 격자

- 12열, 최대 폭 1480px, 좌우 여백 `clamp(16px, 4vw, 56px)`, 열 간격 `clamp(12px, 1.8vw, 28px)`.
- 섹션 머리: 왼쪽 3열은 라벨, 오른쪽 9열은 제목. 라벨은 "이것이 무엇인지", 제목은 "그래서 무엇을 말하는지".
- 큰 단계 사이 간격 `clamp(80px, 11vw, 170px)`. 장 안의 블록 간격은 그 절반 이하. 간격 차이로 묶음을 읽게 한다.

### 3.2 글자

| 역할 | 글꼴 | 이유 |
|---|---|---|
| 본문·제목 | Pretendard | 한글 가독성, 굵기 축이 넓어 큰 제목과 본문을 한 글꼴로 |
| 숫자·번호·연도 | Instrument Serif 기울임 | 숫자를 "사람이 쓴 표기"처럼 보이게 해 표의 차가움을 줄인다. 한글에는 쓰지 않는다 |
| 라벨·메타 | 시스템 고정폭 | 라벨과 본문이 섞이지 않게. 대문자·자간으로 한 단계 낮은 정보임을 표시 |

- 화면 최소 글자 12px (`pnpm check:text-size`가 검사). 본문 16–19px.
- 강조는 `**구절**`. 굵기 + 낮은 형광펜 띠 두 가지를 함께 써서 색만으로 의미를 전달하지 않는다.

### 3.3 색

- 종이 `#eeebe4`, 먹 `#141311`, 신호색 `#ff4d1a` 한 가지.
- 신호색은 면·선·점에만 쓴다(종이 위 대비 2.8:1). 신호색 계열 글자는 `--signal-ink`(4.5:1 이상).
- 어두운 장(`.is-night`)은 같은 토큰을 다시 정의한다. 컴포넌트는 색을 직접 쓰지 않는다.
- 어두운 장은 두 곳뿐이다: Case 01(가장 큰 작업, 리듬의 전환점), 연락처(끝). 더 늘리면 강조가 사라진다.

### 3.4 움직임

- 움직임은 응답일 때만. 자동 재생·스크롤 고정·패럴랙스 없음.
- 첫 화면 제목 등장(한 번), 사례 제목 등장(화면에 들어올 때 한 번), 행 위 반응 200–480ms, 펼침 380ms.
- `prefers-reduced-motion`에서 모두 끈다. 본문은 움직임 때문에 가려지지 않는다.

### 3.5 말투

- 읽는 사람은 오늘 마지막 지원서를 보는 지친 채용 담당자다. 문장은 짧고 단정하게, 한 문장에 한 사실.
- 면책 문장을 쓰지 않는다: "확인되지 않았다", "검증하지 않았다", "직접 비교하지 않는다", "미기재", "설명용 예시" 같은 말. 사실이 아닌 것은 처음부터 주장하지 않으면 되고, 조건은 긍정문으로 쓴다("0.81은 과거로 학습하고 이후 기간으로 평가한 점수입니다").
- 팀 결과는 "팀"이라고 쓴다. 이것은 면책이 아니라 정확한 주어다.
- `check-story.mjs`가 대표적인 면책 표현이 페이지에 나오면 실패한다.

### 3.6 접근성

- 모든 인터랙션은 키보드로 가능하고 포커스가 보인다.
- 스크립트가 없어도 최종 상태가 보인다(분할 데모는 시간순, 슬라이더는 예측 10, 미리보기는 첫 사례).
- 접힌 근거는 네이티브 `details`. 중첩하지 않는다.
- 인쇄는 접힌 내용을 펼쳐서 인쇄한다.

## 4. 섹션별 명세

각 항목: **자리 / 왜 여기 / 담는 것 / 담지 않는 것 / 작은 화면 / 데이터 / 파일**.

### 4.1 머리글

- **자리:** 화면 위 고정. 왼쪽 얼굴+이름, 가운데 장 목록, 오른쪽 "연락하기".
- **왜:** 얼굴은 "사람의 포트폴리오"라는 신호이고, 이름을 바라본다(2.1). 장 목록은 현재 위치를 보여 준다(2.10). 연락하기는 어디서든 한 번에 닿아야 하는 유일한 행동이라 오른쪽 끝(시선이 끝나는 자리)에 둔다.
- **담지 않는 것:** 인쇄 버튼(연락처 장으로 옮김. 머리글은 길 찾기와 연락만).
- **작은 화면:** 장 목록이 둘째 줄로 내려가 가로로 넘긴다. 아래로 스크롤하면 숨는다.
- **어두운 장 위:** 머리글 색이 함께 뒤집힌다.
- **파일:** `StoryLayout.astro`, `masthead.css`, `scripts/story/navigation.ts`

### 4.2 첫 화면 (`#start`)

- **자리:** 메타 줄 / 왼쪽 4열 사진 / 오른쪽 8열에 한 줄 소개 → 큰 제목 → 자기소개 → 숫자.
- **왜:**
  - 사진이 왼쪽인 이유는 2.1. 사진은 오른쪽 열 전체 높이와 맞춰 "이 사람이 이 글의 주인"이라는 관계를 만든다.
  - 한 줄 소개("가능성을 제한하지 않는 개발자, 주연석입니다.")는 본인의 원래 자기 정의다. 이름이 들어 있어 제목보다 먼저 읽힌다.
  - 큰 제목("높은 점수보다 믿을 수 있는 결과를 고릅니다.")은 세 사례의 공통점을 한 문장으로 만든 편집 문장이다. Case 02(0.98을 의심), Case 03(늦은 예측에 더 큰 벌점), Case 01(성능 낮은 데이터 재학습)이 근거다. 근거 없는 형용사가 아니라 아래에서 검증되는 주장이라 가장 크게 둔다.
  - 둘째 줄 "믿을 수 있는"에만 신호색 밑줄. 문장의 핵심어 하나만 칠한다.
  - 자기소개는 2.2의 순서. 숫자는 맨 마지막(주장 뒤의 증거).
- **담지 않는 것:** 기술 스택 아이콘 모음, 자격증 목록(이력 장에 있음).
- **작은 화면:** 사진(작게) + 한 줄 소개가 한 줄에 나란히. 그 아래 제목 → 자기소개 → 숫자 2×2.
- **데이터:** `motto`, `headline`(줄바꿈 유지, 둘째 줄이 강조), `about.*`, `highlights`
- **파일:** `story/Introduction.astro`, `hero.css`

### 4.3 질문 목록 (`#work`)

- **자리:** 첫 화면 바로 아래. 왼쪽 8열 질문 세 줄, 오른쪽 4열 고정 미리보기.
- **왜:**
  - 채용 담당자가 30초 안에 볼 수 있는 마지막 자리다. 여기서 "대표 사례가 무엇이고 내 역할이 무엇인지"가 끝나야 한다.
  - 프로젝트 이름이 아니라 **질문**을 제목으로 쓴다. 읽는 사람이 이미 가진 질문에 답하는 형식이 가장 빨리 읽힌다.
  - 각 줄 = 질문 / 근거 한 줄 / 사례 이름·내 역할. 근거가 질문 바로 옆에 있어야 "왜 이 사례가 이 질문의 답인지"가 한 번에 보인다.
  - 미리보기 칸은 2.6. 기본값은 Case 01.
- **작은 화면:** 미리보기 칸 대신 각 줄에 작은 이미지.
- **데이터:** `projects[].question`, `cardTitle`, `cardRole`, `cover`
- **파일:** `story/Introduction.astro`, `hero.css`, `scripts/story/preview-slot.ts`

### 4.4 사례 (`#nutrition`, `#agriculture`, `#engine`)

순서는 Case 01 서비스(가장 넓은 기여) → Case 02 판단 → Case 03 협업. 가장 큰 작업을 먼저 보여 줘야 뒤의 작은 사례가 "깊이"로 읽힌다.

| 순서 | 블록 | 왜 이 순서인가 |
|---|---|---|
| 1 | 머리 줄: Case 번호 / 답하는 질문 / 발표자료 ↗ | 목록에서 넘어온 사람이 "어느 질문의 답인지" 확인. 근거 링크는 2.3 |
| 2 | 주장형 제목 + 프로젝트 이름·시기·팀 | 사례 전체를 한 문장으로. 이름은 정보, 제목은 주장 |
| 3 | 30초 요약: 내 역할 / 한 일 / 결과 | 한 줄 띠 하나로 사례 판단이 끝나야 한다. 여기까지만 읽어도 된다 |
| 4 | 증거 01–05 (주장 + 표시된 그림) | 2.11. 요약의 각 문장을 그림으로 확인하는 자리 |
| 5 | 내가 맡은 일(먹색 면) / 팀이 함께한 일(점선) | 면의 무게로 기여 비중을 보여 준다 |
| 6 | 과정 전체 읽기 (접힘) | 면접관용. 문제→판단→실행→결과→다음에 한다면, 수치, 상세, 링크 |

- **증거 순서 규칙:** 요약의 "한 일"을 증명하는 그림이 01, "결과"를 증명하는 그림이 마지막. 사람의 판단이 드러나는 그림(누수를 의심한 출력, 비대칭 벌점 곡선 등)은 중간.
- **실제 자료가 설명용 그림을 이긴다:** 직접 그린 설명 그림(세 화면 흐름, 예측값 슬라이더)은 발표자료의 실제 화면·그래프로 바꿨다. 지친 사람에게는 "이 사람이 실제로 만든 것"이 가장 빠른 증거다. 예외는 Case 02의 분할 데모 하나다. 무작위 분할이 왜 미래를 새게 하는지는 실제 출력만으로 보이지 않아, 눌러서 바꿔 보는 그림이 주장 옆에 있다.
- **Case 01만 어두운 이유:** 3.3.
- **데이터:** `projects[].evidence[]` (`claim`, `why`, `visual` 또는 `figure{image,width,height,alt,caption,page,marks[]}`). 표시 좌표는 그림 크기에 대한 0–1 비율.
- **파일:** `story/ProjectCase.astro`, `Exhibit.astro`, `ValidationFlow.astro`, `case.css`, `visuals.css`

### 4.5 그 밖의 작업 (`#archive`)

- **자리:** 세 사례 뒤.
- **왜:** 깊이를 먼저 보여 주고 넓이는 뒤에 둔다. 앞에 오면 "많이 했지만 얕다"로 읽힌다.
- **형태:** 표. 썸네일 / 제목 / 분야 / 기간·형태 / 주요 기술. 행을 누르면 그 자리에서 펼친다.
- **썸네일을 늘 보이는 이유:** 2.6. 마우스 없이도 같은 정보.
- **담는 것:** 팀 프로젝트는 "개인 기여 상세 미기재"를 명시한다.
- **파일:** `story/Archive.astro`, `sections.css`

### 4.6 연표 (`#timeline`)

- **자리:** 작업 목록 뒤, 이력 앞.
- **왜:** 작업 목록이 "무엇을"이라면 연표는 "얼마나 꾸준히". 이력(과거 직업)으로 넘어가기 전의 다리.
- **제목:** "열한 달 동안, 열한 개의 프로젝트." 2025년 2–12월(11개월)에 연표의 2025년 작업 11개가 놓인다. 연도 머리의 원문 문장("쉬지 않고 달려왔습니다")과 겹치지 않게, 제목은 숫자로 요약하고 목소리는 연도 머리에 맡긴다.
- **형태:** 연도 머리(연도 + 그해의 한 줄) → 달별 항목. 교육은 굵게, 자격은 신호색 글자와 "자격" 표시, 작업은 보통. 현재 연도(2026)와 진행 중 항목은 신호색 점.
- **자격 날짜:** 두 자료에서 다른 자격(ADsP, 정보처리기사 필기)은 연표에 넣지 않는다(`recordNote`).
- **데이터:** `timelineYears`, `timeline[].items[].kind`
- **파일:** `story/Timeline.astro`, `sections.css`

### 4.7 이력 (`#background`)

- **자리:** 끝에서 두 번째.
- **왜:** 개발 이전 경력(임상연구 데이터 모니터링, 데이터 라벨링 검수)은 "데이터를 의심하는 습관"의 배경이다. 사례를 본 뒤에 읽어야 연결이 보인다. 앞에 오면 "개발 경력이 아니다"로만 읽힌다.
- **형태:** 경력(가장 넓게) / 학력·교육 / 자격. 상세와 해커톤은 접힘.
- **파일:** `story/Background.astro`, `sections.css`

### 4.8 연락처 (`#contact`)

- **자리:** 끝, 어두운 장.
- **왜:** 2.5. 인사 → 이메일(가장 큰 링크) → 복사·GitHub·PDF.
- **PDF 버튼이 여기 있는 이유:** 다 읽은 사람이 "저장해서 공유"하는 시점이 끝이다.
- **담지 않는 것:** 전화번호(공개 빌드 검사가 막는다).
- **파일:** `StoryLayout.astro`, `contact.css`, `scripts/story/contact.ts`, `printing.ts`
