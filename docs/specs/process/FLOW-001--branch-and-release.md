# FLOW-001 · 브랜치와 반영 흐름

공통 규칙: RULE-SPEC. 선택 이유: ADR-0001. 실행 절차: OPS-001.

## 범위

이 저장소의 장기 브랜치, 작업 반영, 배포 경로.

## 브랜치

| 브랜치 | 역할 | 직접 커밋 | 배포 |
|---|---|---|---|
| `main` | 공개된 상태. 커밋 하나 = 반영 하나 | 금지(스쿼시 머지만) | GitHub Pages |
| `dev` | 작업 통합. 관심사별 커밋을 쌓는다 | 허용 | 검증만 |

- 로컬·원격·워크트리에는 `main`, `dev`만 유지한다. 임시 브랜치·워크트리는 `dev`에 합친 뒤 같은 날 삭제한다.
- `dev/…`처럼 장기 브랜치 이름을 접두어로 쓰는 브랜치는 만들지 않는다(`dev` ref와 충돌).

## 반영 (dev → main)

- 사전 조건: `dev`의 작업 트리가 깨끗하고 `pnpm verify`·e2e가 통과한다. `dev`가 `main`을 이미 포함한다.
- 입력: 이번 반영에 들어갈 `dev` 커밋들.
- 기대 동작
  1. `main`에 `dev`를 **스쿼시 머지**한다. 메시지 제목은 반영 요약, 본문은 포함된 관심사 목록.
  2. 곧바로 `main`을 `dev`에 **일반 머지**(`--no-ff`)해 두 브랜치의 이력을 다시 잇는다.
  3. 둘 다 원격에 푸시한다. `main` 푸시가 배포를 시작한다.
- 완료 기준: `git diff main dev`가 비고, `git merge-base --is-ancestor main dev`가 성공한다.

## 실패 복구

- 스쿼시 충돌: `main`에서 머지를 취소하고 `dev`에 `main`을 먼저 머지해 충돌을 해결한 뒤 다시 반영한다.
- 2단계 누락(`dev`가 `main`을 포함하지 않음): 다음 스쿼시에 이미 반영된 변경이 다시 충돌로 나온다. 반영 전에 `main` → `dev` 머지부터 한다.
- 배포 실패: `main`을 되돌리지 않고 `dev`에서 고쳐 다시 반영한다.

## 검증

- 배포 워크플로는 `main` 푸시에서만 배포하고, `dev`는 검증만 한다(`.github/workflows/deploy.yml`).
- 브랜치 목록 점검: `git branch -a`에 `main`, `dev`(와 원격 대응)만 있다.
